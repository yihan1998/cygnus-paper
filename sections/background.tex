\subsection{Existing Preemption Models}
\label{subsec:existing-preemption-models}

\paragraph{Triggered Path}
Even though dataplane OSes commonly use preemptive scheduling to reduce tail latency, they differ in the path where preemption takes place.
Some systems~\cite{prekas2017zygos,fried2020caladan,lin2024fast} trigger preemption on the \textit{control path}, where preemption is used to balance load across cores or adjust core allocation for applications.
Since control path preemption does not directly affect latency-critical tasks, it has more relaxed timing requirements.
Other systems~\cite{kaffes2019shinjuku,iyer2023achieving} trigger preemption on the \textit{datapath}, where preemption directly affects latency-sensitive tasks.
Datapath preemption requires precise timing to ensure latency-sensitive tasks receive timely execution and low overhead to avoid excessive disruption to the datapath.

\paragraph{Topology}
Preemption can be issued using either a \textit{centralized} or \textit{distributed} topology.
In a centralized topology, a dedicated dispatcher issues preemptions to remote worker cores.
For instance, Shinjuku~\cite{kaffes2019shinjuku} and Concord~\cite{iyer2023achieving} use a centralized dispatcher to preempt remote cores on the datapath to approximate a hybrid of central First-Come-First-Served (FCFS) and Processor Sharing (PS) scheduling.
In a distributed topology, each core is responsible for issuing preemptions to itself.
For example, an idle worker core in ZygOS~\cite{prekas2017zygos} could preempt a remote busy core, forcing it to execute network stack and replenish its work queue with new application tasks.
Then the idle core can steal tasks from the busy core to balance load across cores.

\paragraph{Mechanism}
Existing dataplane OSes use various mechanisms to implement preemption, each with different trade-offs in terms of latency and overhead.
A prevalent mechanism is the \textit{Inter-Processor Interrupt} (IPI), which allows one core to interrupt another core by sending a special interrupt signal.
Shinjuku~\cite{kaffes2019shinjuku} and ZygOS~\cite{prekas2017zygos} use unicast IPIs to preempt remote cores on the datapath and control path, respectively.
Caladan~\cite{fried2020caladan} uses multicast IPIs to notify multiple cores of the core adjustment decision, amortizing the per-core preemption overhead.
A new mechanism is \textit{cache-coherent messaging} from Concord~\cite{iyer2023achieving}, which leverages cache coherence protocols to set preemption flag in the target core's cache line.
This allows low-overhead, cooperative preemption.

\paragraph{Application cooperation}
Most existing dataplane OSes do not require application cooperation for preemption.
Both IPI and User Interrupt mechanisms guarantee immediate preemption of the target core, regardless of the application's state.
Concord~\cite{iyer2023achieving} is an exception, since it uses cooperative preemption via cache-coherent messaging.
This mechanism relies on the application to periodically poll the cache line for preemption flags and explicitly yield control to the scheduler.
While this reduces preemption overhead, it risks missing preemption deadlines.
If the compiler failed to insert these polling points at appropriate locations, for instance in third-party libraries, the application would not be preempted in time, leading to potential tail latency SLO violations.

\subsection{Existing Isolation Models}
\label{subsec:existing-isolation-models}

\paragraph{Between application and scheduler}
Many dataplane OSes~\cite{kaffes2019shinjuku,zhang2021demikernel,iyer2023achieving} adopt \textit{single address space} architecture where the application and scheduler share the same memory space.
They execute both the application and the scheduler in Ring 3 without memory isolation.
This design prioritizes performance by implicitly assuming a trusted application model.
however, it leaves the system fragile, as any bug in the application can corrupt the scheduler's state.
To restore safety, systems like IX~\cite{belay2014ix} and ZygOS~\cite{prekas2017zygos} leverage hardware virtualization to run the scheduler in Ring 0 (non-root) mode, strictly isolating it from Ring 3 applications.
However, the ring transitions ($\texttt{VMEXIT}$/$\texttt{VMENTER}$) are still expensive, often necessitating request batching that degrades tail latency.
More recently, Vessel~\cite{lin2024fast} leverages MPK to provide lightweight isolation between user processes and scheduler within the same address space.
User processes of an application execute with restricted permissions, accessing only the memory region associated with a single protection key assigned to it.
In contrast, the scheduler operates in a privileged mode with access enabled for all protection keys to perform user process switching.

\paragraph{Between applications}
To isolate multiple applications running on the same dataplane OS, most existing systems~\cite{belay2014ix,prekas2017zygos,fried2020caladan} rely on strong isolation provided by the kernel.
Each application runs as a separate kernel process, with its own virtual address space and protected resources.
This model ensures robust isolation between applications, preventing interference and security breaches.
Vessel~\cite{lin2024fast} takes a different approach by using MPK to isolate applications within the same address space.
Each application is assigned a unique protection key, and memory regions are tagged with the corresponding keys.
This allows for extremely lightweight context switching between applications, as the system only needs to change the active protection key rather than performing a full address space switch via TLB flushes.
