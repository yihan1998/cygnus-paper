Our goal is to design a new dataplane operating system architecture that enables scalable, microsecond-scale preemptive scheduling on modern multi-core servers.
Achieving this goal requires reconciling a fundamental tension: delivering near bare-metal performance for fine-grained scheduling, while ensuring system safety when exposing low-level hardware primitives (e.g., LAPIC timers) to untrusted userspace schedulers.
We identify two major challenges in bridging this gap:

\paragraph{C\#1: Virtualization-based isolation incurs prohibitive overhead for microsecond-scale scheduling.}
Existing virtualization techniques (e.g., APICv) provide strong isolation between physical hardware and untrusted userspace code.
However, these mechanisms introduce substantial overheads on critical datapath operations, making them unsuitable for microsecond-scale preemptive scheduling.
Table \ref{tab:operation-overhead} quantifies the overhead of several key operations required for APIC-based preemptive scheduling on bare metal and under virtualization.
A bare-metal \texttt{SYSCALL} completes in 151 cycles, while the equivalent VMCALL is 43$\times$ higher even with APICv.
Arming a local APIC timer with \texttt{hrtimer\_start} takes 490 cycles on bare metal, but 11.5$\times$ higher with APICv and 20$\times$ higher without APICv.
Interrupt delivery in bare metal and with APICv are comparable since APICv avoids \texttt{VMEXIT} and \texttt{VMENTRY}.
But the delivery cost soars 2$\times$ higher without APICv.

\paragraph{C\#2: Safely multiplexing system-critical hardware between the kernel and untrusted userspace.}
Granting userspace schedulers direct access to system-critical hardware resources risks breaking isolation guarantees and compromising overall system integrity.
Unlike I/O devices, which can often be assigned exclusively to a single VM, LAPIC timers remain integral to core system functions, including watchdogs and kernel scheduling.
Recklessly exposing it to untrusted userspace creates opportunities for malicious or buggy application code to disrupt system operation, for example by causing softlocks or triggering preemption storms.

\subsection{\kernel Approach}

To mitigate the above threats, \kernel employs a combination of hardware-assisted isolation, strict identity verification, and control-flow integrity mechanisms.

To address C\#1, \kernel uses Intel MPK to partition the single process address space into two hardware-enforced domains.
The Tenant Ring contains all untrusted application code and data, as well as the normal userspace components of the library OS for system call handling and user thread management.
The Shadow Ring contains the trusted scheduler (\schedcore), its private state, and its text segment. 
A critical security requirement is that the \texttt{WRPKRU} instruction, which switches access to the Shadow Ring, must exist only within the verified scheduler code.
To enforce this, the \kmod performs a \textit{load-time binary verification} during initialization. 
It scans the loaded \texttt{.text} segment of the untrusted application binary for the opcode sequence of the \texttt{WRPKRU} instruction. 
The verification passes only if the opcode appears exactly once at the expected offset within the secure trampoline function, confirming that no unauthorized instance has been injected. 
Following successful attestation, the \kmod assists in configuring the MPK partition and seals it by installing a \texttt{seccomp} filter. This filter permanently revokes the \texttt{pkey\_*} system call interface, rendering the MPK domain assignment immutable and preventing a tenant from altering the memory map to gain entry.

To address C\#2, \kernel introduces a Double-Gate security model to goven the interactions between the untrusted tenant, the trusted scheduler, and the kernel.
This model ensures that while the \schedcore operates with direct hardware access, the untrusted tenant is confined to its domain, and all cross-privilege operations are authenticated and integrity-checked.
