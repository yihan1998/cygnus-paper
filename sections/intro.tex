Modern cloud services, including web search, online retail, and serverless platforms, operate under microsecond-scale latency Service Level Objectives (SLOs) \cite{barroso2017attack,kaffes2019shinjuku,marty2019snap,zhang2021demikernel,iyer2023achieving}.
With every user request fanned out across thousands of servers, the end-to-end response time is determined by the slowest server.
Therefore, to ensure a satisfactory end-to-end responsiveness, bounding tail latency at each individual server is crucial.
The stringent tail latency SLOs further tighten into microsecond regime by the widespread deployment of ultra-low latency hardware \yihan{cite} and the proliferation of microservice architectures \yihan{cite}.

Unfortunately, general-purpose operating systems (OSes) such as Linux struggle to meet these stringent tail latency SLOs due to high and unpredictable overheads in the kernel I/O stack and scheduler.
To compensate, prior systems proposed \textit{kernel bypass} to obtain low and predictable latency on the datapath, hence introduces the concept of \textit{dataplane OS}.
Dataplane OSes are able to directly access network devices in userspace and tailor a lightweight I/O stack for target workloads.
Systems such as IX~\cite{belay2014ix} use hardware virtualization features like Intel VT-d~\cite{} to achieve protected, direct NIC queue access.
Other systems such as Shenango~\cite{} and Persephone~\cite{} rely on high-performance user-space I/O libraries such as the Data Plane Development Kit (DPDK)~\cite{}.
Dataplane OSes also implement user-level thread management to eliminate the unpredictable scheduling delays in kernel space.
For instance, IX adopts a single-threaded, run-to-completion model, where the thread mitigates ring privilege switching overhead via adaptive batching.
Systems such as Arachne~\cite{} and Shenango~\cite{} use cooperative multithreading, where user-level threads yield explicitly to the runtime.

Yet kernel bypassing alone is insufficient, as neither run-to-completion or cooperative scheduling can prevent head-of-line blocking in dataplane OS under the high-dispersion workloads common in cloud services.
To compensate, dataplane OSes must implement \textit{preemptive scheduling} to approximate Processor Sharing (PS), which is theoretically optimal for heavy-tailed workloads.
State-of-the-art dataplane OSes have explored various approaches to implement microsecond-scale preemptive scheduling.
\yihan{For example, Shinjuku leverages unicast Interprocessor Interrupts (IPIs) to preempt tasks who have exhausted their 5$\mu$s timeslices.

However, most dataplane OSes rely on a \textit{centralized dispatcher} to issue preemptions, embedding a hidden scalability bottleneck as the number of cores continues to increase in modern multi-core servers. 
The centralized preemption dispatcher faces a fundamental dilemma: 
it must balance preemption precision against preemption issuing overhead.
On one hand, issuing preemptions individually ensures microsecond-scale precision but incurs preemption issuing overhead that grows linearly with core count. 
On the other hand, batching preemptions reduces overhead but introduces timing skew across cores, leading to inconsistent timeslicing, and potential SLO violations.
To mitigate this dilemma, the dataplane OS could reserve additional cores solely for preemption issuing to guarantee preemption precision.
This creates a compounded scalability challenge: preserving preemption precision both increases preemption issuing overhead and reduces core efficiency.

In this work, we address the scalability dilemma with \sysname, a new dataplane OS architecture.
Our key insight is that modern processors already include the necessary hardware for fine-grained, per-core preemption-namely, the Local Advanced Programmable Interrupt Controller (LAPIC) timer.
However, the LAPIC timer is traditionally managed exclusively by the kernel to schedule kernel threads, making it inaccessible to userspace code.
Thus, instead of introducing new hardware features, \sysname asks the following question:
\textit{How to safely expose system-critical hardware resources like the LAPIC timer to the dataplane OS scheduler?}

To answer this, \sysname follows an Exokernel design philosophy: 
system-critical hardware resources can be directly managed by the dataplane OS scheduler, but the privileged logic that manipulates these resources is strictly isolated from untrusted application code and other dataplane components.
Specifically, \sysname introduces the \textit{Shadow Ring}, a logically privileged execution context implemented entirely in Ring 3.
It uses Memory Protection Keys (MPK) to isolate the data and text segments of the trusted scheduler from untrusted context in a lightweight manner.
The \sysname scheduler is therefore split into two parts:
\begin{enumerate*}[label=(\alph*)]
  \item an untrusted part that manages user-level threads and executes alongside application code, and
  \item a trusted part (\schedcore), which runs within the MPK-isolated Shadow Ring and interacts directly with critical hardware resources.
\end{enumerate*}

Since system-critical hardware resources still require privileged access in modern operating systems, \sysname relies on a kernel module (\kmod) as a secure mediation layer between \schedcore and the underlying hardware.
To configure a hardware resource, \schedcore can either 
\begin{enumerate*}[label=(\arabic*)]
  \item issue a \textit{downcall} via a system call (e.g., \texttt{ioctl()}) that traps into Ring 0, where \kmod completes hardware configuration, and
  \item directly write to memory-mapped I/O (MMIO) regions of the hardware, which is mapped into a MPK-protected data segment in the Shadow Ring.
\end{enumerate*}
When a hardware event such as a timer expiration occurs, \kmod delivers it to the scheduler via an \textit{upcall}, transferring control to a registered handler located in the MPK-protected text segment in the Shadow Ring.
